# ElementInternals and axe-core testing

Spectrum Web Components form fields participate in forms and expose their accessible name, help text, and error text through [`ElementInternals`](https://developer.mozilla.org/en-US/docs/Web/API/ElementInternals) rather than a nested light-DOM `<input>`. If your own test suite runs [axe-core](https://github.com/dequelabs/axe-core) against pages that include these components, this pattern can surface false positives you'll need to account for. This guide covers what browsers and assistive technology expose versus what a static analyzer can see, where axe-core currently has gaps, and how to scope a false positive in your own tests. For general cross-root ARIA background, see [Semantic HTML and ARIA](/docs/guides-accessibility-semantic-html-and-aria--docs).

## What browsers and assistive technology see versus what axe-core sees

Browsers build the accessibility tree from whatever a component actually does at runtime: `ElementInternals` ARIA properties (`internals.role`, `internals.ariaLabel`), reflected element-reference properties (`ariaLabelledByElements`, `ariaDescribedByElements`), and the resulting computed name and description. Assistive technology reads that computed tree, so a correctly wired form field is announced correctly regardless of where its role or label association lives in the DOM.

**axe-core** is a static analyzer. It inspects DOM structure and attributes rather than the fully computed accessibility tree, so it has historically been unable to follow relationships set through `ElementInternals` or through element-reference properties that point across a shadow boundary. A component can be fully accessible to real assistive technology while still failing (or silently passing) an axe-core rule that cannot see how the relationship was established.

## axe-core's ElementInternals support

Newer versions of axe-core read ARIA _values_ set through `ElementInternals` (`internals.role`, `internals.ariaLabel`, and similar) across most checks (`aria`, `label`, `navigation`, `forms`, `tables`), and add [`getResolvedRefs`](https://github.com/dequelabs/axe-core/pull/5151), which resolves raw IDREF attributes to virtual nodes. This is the foundation the [community protocol](https://wicg.github.io/aom/aria-reflection-explainer.html) (the WICG Accessibility Object Model's ARIA reflection work, part of the ARIA 1.2 spec) needs for a static analyzer to eventually follow a cross-root element-reference property, but that specific piece, the `label` check reading `ariaLabelledByElements`, is not yet part of it; see the known false positive below.

⚠️ **Important:** Check your installed axe-core version's [changelog](https://github.com/dequelabs/axe-core/blob/develop/CHANGELOG.md) before relying on this support, and don't treat any version as a guarantee that every `ElementInternals` pattern validates correctly. Several related issues remain open upstream at the time of writing, including [`label` should check `ariaLabelledByElements` as well](https://github.com/dequelabs/axe-core/issues/4943), [update `getAccessibleRefs`](https://github.com/dequelabs/axe-core/issues/5210) and [its ElementInternals support](https://github.com/dequelabs/axe-core/issues/5222), and [ElementInternals ARIA role conflict resolution](https://github.com/dequelabs/axe-core/issues/5162). Verify a specific false positive is actually fixed by re-running your test without the exclusion before removing it; don't assume an axe-core upgrade alone resolved it. Deque's [`elementInternals`-labeled issues](https://github.com/dequelabs/axe-core/issues?q=is%3Aissue+label%3AelementInternals) are the best source for current status.

Cross-root IDREF resolution specifically (an `aria-describedby` in the light DOM pointing at an element inside a different component's shadow root) depends on this same reflection work and may continue to trail general same-root `ElementInternals` support; check the linked issues rather than this document for the current state.

## Known false positives and blind spots

Spectrum form fields set their labelling relationship through `ElementInternals` on an inner shadow control. Depending on your axe-core version, this can surface as a roleless host reporting "Form element does not have a label" even though the field is correctly labeled and announced by assistive technology. That's a known upstream gap ([axe-core#4943](https://github.com/dequelabs/axe-core/issues/4943), open at the time of writing), not a bug in the component; treat it as a live false positive rather than something a version bump has already fixed. Known blind spots, like a misconfigured `accessible-labelledby` silently yielding a missing label, are not flagged by axe-core at all; manual and screen reader testing remain authoritative for those (see [Screen reader testing](/docs/guides-accessibility-screen-reader-testing--docs)).

## Scoping a false positive in your own tests

When axe-core reports a violation against one of these components that you believe is a false positive for the reasons above:

1. Confirm it against the linked upstream issue rather than assuming; re-test after any axe-core upgrade before keeping an old exclusion.
2. Add a rule-scoped exclusion in your own axe-core configuration (for example, `context.exclude` with `@axe-core/playwright`, or a `rules` override with `jest-axe`), not a blanket rule disable.
3. Include a comment linking the relevant upstream axe-core issue next to the exclusion, and revisit it when you upgrade axe-core; remove it once the linked issue ships a fix you've verified.
4. Verify exposure with manual assistive technology testing, particularly in Firefox, which handles `ElementInternals` ARIA less consistently than Chromium and Safari.
