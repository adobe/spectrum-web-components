## Anatomy

A text field consists of:

- **Input**: the real, focusable `<input>` that carries the value and native `textbox` role
- **Label** (optional), provided through the `label` slot: visible text rendered as a real, same-root `<label for>`
- **Necessity indicator** (optional): an asterisk (`icon`) or `(required)`/`(optional)` text (`label`) appended to the label, controlled by `necessity-indicator` (see [Necessity indicator](#necessity-indicator))
- **Validation icon**: a decorative alert icon shown at the trailing edge of the input while `field-status="invalid"`
- **Description** (optional), provided through the `description` slot: guidance text associated via `aria-describedby`
- **Error text** (optional), provided through the `error-text` slot: shown in place of the description and associated via `aria-describedby` only while `field-status="invalid"`

## Options

The supported input types are `text`, `url`, `tel`, `email`, and `password`. Unsupported values render as `text` and produce an enum-validation warning in debug mode.

### Labelling

Three sources can provide the field's accessible name. When more than one is set, the browser's [accessible-name computation](https://www.w3.org/TR/accname-1.2/) decides which one is announced, in this order:

1. **`accessible-labelledby`** (highest precedence): space-separated element `id`s, resolved against the field's root node, for composing a name from elements the field does not own (for example, a grid cell named by its row and column headers).
2. **`accessible-label`**: a string accessible name for a field with no visible label of its own.
3. **A slotted `label`** (lowest precedence): the default, recommended path for an ordinary standalone field. Renders as a real, same-root `<label for>`, giving native click-to-focus.

The examples follow precedence order. Each table input combines its row and column headers: Billing and City produce "Billing City".

### Sizes

Text fields come in four sizes. Size controls the field height, typography, inline padding, corner radius, and default maximum width. The control reserves space for the invalid icon and its gap, so showing validation does not change the field width.

<Canvas of={TextFieldStories.Sizes} />

### Label positions

The `label-position` attribute places the label above the input (`top`, the default) or beside it (`side`).

In `side` position, the input aligns with the label's first line. A short label reads as centered against the input; a long label grows downward while the input stays aligned with its first line.

<Canvas of={TextFieldStories.LabelPositions} />

### Necessity indicator

`necessity-indicator` chooses how the field's necessity is marked in the visible label. The default, `icon`, appends a decorative asterisk to required fields only. `label` appends `(required)` to required fields and `(optional)` to optional ones, marking both; use it when most fields in a form share the opposite state (Spectrum's [required or optional](https://spectrum.adobe.com/web/rsp/components/text-field#usage-guidelines) pattern). The indicator needs a visible label. Text indicators contribute to the accessible name; the input's native `required` state also conveys the requirement.

<Canvas of={TextFieldStories.NecessityIndicator} />

### Prefix

The `prefix` slot places non-interactive content before the input, inside the field: a symbol (like a currency `$`), an icon, or an avatar. Slotted icons auto-size to the field; other content keeps its own size. Clicking the prefix focuses the input.

## States

Use `fieldStatus` (the `field-status` attribute) for one authored status: `disabled`, `invalid`, `valid`, or `readonly`. The default is `undefined`, not `valid`. Assigning another status replaces the previous one; assign `undefined` or remove the attribute to return to the default. The former `disabled`, `readonly`, `invalid`, and `valid` boolean properties are not supported. `required` remains independent.

### Default

The default state is editable and accepts keyboard input.

<Canvas of={TextFieldStories.Default} />

### Required

`required` sets the native input's required state and prevents an empty field from passing constraint validation. With a visible label, the default necessity indicator adds a decorative asterisk. The input uses native `required`, not a separate `aria-required`.

<Canvas of={TextFieldStories.Required} />

### Disabled

`field-status="disabled"` retains the field's value but prevents editing and <kbd>Tab</kbd> access. The field does not block form validation and is excluded from `FormData`.

<Canvas of={TextFieldStories.Disabled} />

### Read-only

`field-status="readonly"` keeps the field focusable and its value selectable, but not editable. Unlike a disabled field, it remains in the tab order and in `FormData`. It does not block validation.

<Canvas of={TextFieldStories.ReadOnly} />

### Invalid

`field-status="invalid"` hides the description and shows the slotted `error-text` when supplied, associating it via `aria-describedby`. Without error text, no inline message is shown; the invalid border and icon remain. The status blocks native constraint validation and submission when the field is eligible for validation. The application controls this state; native validation failures do not enable it automatically.

<Canvas of={TextFieldStories.Invalid} />

### Valid

`field-status="valid"` records an application-authored valid status without bypassing native constraints or custom validation errors. It does not show a checkmark; that visual remains deferred.

<Canvas of={TextFieldStories.Valid} />

## Behaviors

### Label overflow

A long visible label wraps onto multiple lines instead of clipping. The top-label example constrains one field inside a 180px container. The side-label examples each use a 260px host; their labels wrap within a column capped at 50% of the host width by default, or at the value of `--swc-field-label-max-inline-size`.

The host's `inline-size` controls the space available to the layout, not the control's maximum width. The control can shrink with a narrower container, but stops growing at the default maximum for its size. To let it fill a wider host, also set `--swc-field-input-max-inline-size: 100%`.

<Canvas of={TextFieldStories.LabelOverflow} />

### Form participation

`swc-text-field` participates in native forms through constraint validation, reset, and `FormData`. This example uses `novalidate` and an application submit handler to show inline errors instead of browser validation bubbles. The handler accepts data only when the field passes validation; it does not navigate or send data to a server.

`field-status="invalid"` shows the inline error and sets `validity.customError`, making eligible fields fail validation. The application must clear or replace this status explicitly; input, blur, and submission do not clear it automatically. Disabled and read-only fields do not block submission.

`setCustomValidity(message)` adds an application-specific error without changing `fieldStatus` or inline error presentation. Clear it with `setCustomValidity('')`. Authored invalid status, custom messages, and native constraints are independent. Pre-render calls are preserved; after rendering, custom validity updates immediately. Reactive property changes take effect after `updateComplete`.

`validationMessage` uses the custom message, or "Invalid value." for an authored invalid status without one. Supply a localized custom message when needed. Slotted `error-text` is separate; native validation failures do not automatically show it or set `fieldStatus`.

```js
field.setCustomValidity('Username is already taken.');
field.fieldStatus = 'invalid';
await field.updateComplete;

// Clear both errors.
field.setCustomValidity('');
field.fieldStatus = undefined;
await field.updateComplete;
```

This demo clears its own invalid status before revalidating on Submit. A rejected attempt replaces the previous submission result with a blocked message. Submit refreshes the latest validation result after updating `fieldStatus`; Check validity refreshes it on demand. Both panels are snapshots, not live state. Reset restores the value and panels but preserves authored errors.

Pressing <kbd>Enter</kbd> activates the form's first associated submit button, including a button outside the form linked by its `form` attribute. A disabled default button prevents submission. Without a submit button, a form submits only when the text field is its sole input that blocks implicit submission; additional native text-like inputs or `swc-text-field` elements prevent it. Composition input does not trigger submission, and consumers can cancel it with `preventDefault()` on the `keydown` event.

Values follow the native input type's sanitization rules. Single-line inputs remove line breaks; email and URL inputs also remove leading and trailing ASCII whitespace. After an update, the `value` property, displayed input, and submitted form value agree. Programmatic value changes and form resets do not emit `input` or `change` events.

When the browser supplies saved string state through `formStateRestoreCallback()`, the field restores its value using the same sanitization rules without emitting `input` or `change` events. Restoration leaves the authored `value` attribute unchanged, so a later form reset still restores the initial value. Browser support for invoking this callback during navigation or autofill varies.

## Accessibility

### Features

- **Native role**: the host sets no ARIA role; the real `<input>` supplies the implicit `textbox` role.
- **Browser-resolved name**: each source is wired independently, and the browser's accessible-name computation picks the one that is announced, in the order `accessible-labelledby` &gt; `accessible-label` &gt; slotted label. A slotted visible label always renders as a real `<label for>`, keeping native click-to-focus.
- **Combining descriptions**: a slotted `description` and an external `accessible-describedby` reference combine rather than override each other; the in-shadow description comes first.
- **Error text replaces the description while invalid**: the slotted `error-text` replaces the description while `field-status="invalid"`, so `aria-describedby` references only the message on screen rather than pointing at the error separately via `aria-errormessage`, since AT support for that attribute is still inconsistent.
- **Dev-mode warnings**: a field with no visible label, no `accessible-label`, and no `accessible-labelledby` triggers a console warning, and so does a field that sets both `accessible-labelledby` and `accessible-label`.

> **Known axe-core false positive.** A field named only via `accessible-labelledby` fails automated axe-core scans with a "Form element does not have a label" (`label` rule) violation, even though the name resolves correctly in real browsers and assistive technology. axe-core inspects DOM attributes and has no standardized way to read `ariaLabelledByElements`, the ARIA element-reflection API in use.

### Best practices

- Prefer a slotted `label` for ordinary fields; reserve `accessible-label`/`accessible-labelledby` for fields with no visible label of their own or a name composed from elements the field doesn't own.
- When a field has both a visible label and a programmatic name, make sure the programmatic name contains the visible text, per [Label in Name (2.5.3)](https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html). Do not set both `accessible-label` and `accessible-labelledby`; a dev-mode warning flags that combination.
- Set `autocomplete` when a field collects a recognized personal-data type, such as `email` or `billing street-address`, so browsers and assistive technology can identify its purpose and offer appropriate autofill. See [`autocomplete` HTML attribute (MDN)](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/autocomplete).
- Always pair `field-status="invalid"` with slotted `error-text` so the invalid state is not conveyed by color or the validation icon alone.
- Use `accessible-describedby` for a description composed from light-DOM content the field doesn't own; it combines with, rather than replaces, a slotted `description`.
