# Test audit

Adapted from [OpenClaw's test-audit skill](https://github.com/openclaw/openclaw/blob/main/.agents/skills/test-audit/SKILL.md) under the MIT license in [LICENSE](LICENSE).

Use authoring mode for each new or changed test. Use audit mode for a focused sweep of tests that repeat stronger proof, assert implementation instead of behavior, or require test-only production seams. A whole-subsystem campaign requires [CAMPAIGN.md](CAMPAIGN.md); do not claim campaign coverage from a focused audit.

## Authoring gate

Before adding a test, answer:

1. What observable behavior, invariant, or independent contract does it protect?
2. What credible regression makes it fail?
3. Why does existing coverage not already catch that failure? Give each contract one primary test owner at the strongest boundary. Another layer needs its own distinct risk, such as transport or lifecycle failure. Prefer extending a table or fixture over adding a near-duplicate.
4. Does it require an export, flag, wrapper, or injection hook with no production caller? If so, test at the real boundary instead.

Reject a test matching a junk pattern unless the retention bar identifies its independent contract. A test that breaks under behavior-preserving refactoring asserts implementation, not behavior. A bug regression test must fail on the pre-fix code for the intended reason and pass after the owner-boundary fix.

## Junk patterns

- Assertion-free coverage probes, self-comparisons, or identity copiers.
- Copied fixtures, inventories, manifests, or export lists; exact source, import, or string greps.
- Private predicate or call-shape tests duplicated at real boundaries; duplicate invocations of the same contract.
- Provider-local replays of shared helpers; tests maintained only for test-only exports, globals, or wrappers.
- Dead production code with only test callers.
- Expected values generated by the helper or renderer under test.
- Mocks that implement the asserted behavior, or one identical mock standing in for different APIs.
- Fixtures that produce receipts or callback ordering the owner should produce; persistence checks against a store the path never writes.
- Capability tests that repeat flags without exercising the promised behavior.
- Negative controls that pass because of a different guard or an unreachable rejection.
- Names or fixtures that claim behavior the input does not exercise.

## Value and retention bars

Before judging a candidate, read the complete test and production owner, entry point, callers, sibling implementations, overlapping tests, test routing, and relevant history. For dependency-backed behavior, inspect dependency source or types.

Retain tests that independently guard a public API, protocol, config, migration, storage, security, platform, default, generated output, package, release, or architecture contract. Keep observable call ordering and credible regressions. A source-inspection test can be the cheapest independent guard if it survives identifier-only refactoring and fails when the contract changes. A baseline failure may indicate a product bug; reproduce it rather than deleting the test. Slow or static tests are not automatically low value.

## Audit workflow

Keep discovery read-only and report evidence before editing. For a broad scope, inspect separate owner areas in parallel when useful. Outside campaign mode, prefer a few high-confidence candidates to a speculative inventory.

For each deletion candidate, record:

- Exact test name and location, and what failure it can detect.
- Non-test callers of the production code or support seam.
- Stronger remaining owner-boundary proof, or why none is needed.
- Relevant history and why the test or seam exists.
- Production or test-support deletion unlocked, risk, and focused validation command.

Edit one coherent owner-boundary batch. Remove obsolete test-only exports and dead production paths rather than preserving aliases. Move retained regressions to their canonical owner; do not replace deleted tests with more implementation assertions. Prefer fewer production lines, but do not delete uncertain contracts to inflate the count.

## Validation in this repository

Do not edit tests or source while the test runner is active. From the repository root:

1. Run the smallest owning and sibling suites with `yarn workspace <package-name> test <test-file>`; use the relevant package's `package.json` for scripts. Browser/Storybook tests use their configured runner, not Vitest by default.
2. For removed source greps or plan assertions, run the executable build, script, or dry-run that owns the contract.
3. Check changed files with `yarn prettier --check <paths>`, targeted ESLint where applicable, `yarn lint:ai` for `.ai/` changes, and `git diff --check`.
4. Inspect `git diff --numstat` and report production/tooling separately from tests and test support. Run broader suites when the owner boundary or change requires them.
5. Review the final diff for coverage gaps and confirm each moved assertion can fail for a credible regression.

## Handoff

Report the low-value categories removed, owner simplifications, false positives retained, proof actually run, production versus test line changes, and named follow-ups. Commit or open a pull request only when requested.
